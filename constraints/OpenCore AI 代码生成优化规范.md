# OpenCore AI-Assist Generating Formula<br>AI辅助代码生成优化规范


## 根本原则

+ 重要的修改，任何可能干扰到OpenCore的API接口和ABI签名的操作一定要征得用户同意，若有可能需要grill-me反复推敲。



## 生成时代码规范

### 注释生成

应当符合我们在优化时代码规范中提到的注释规范

### 不要随意加入工具方法

对于复用可能性不高的可抽象成工具方法的代码逻辑，不要将其抽出来作为工具方法，只需要使用region来标注即可。

即便对于高复用可能性的逻辑，也要征求用户同意，再进行抽离。

### 不要Emoji和表情

### 复杂逻辑生成时提醒

在生成一些复杂的逻辑时，或者构造庞大系统的时候，应当依托类似grill-me这样的skill（换句话说，和用户反复推敲）。

要拆分即将生成的复杂逻辑的概念，将其通知用户。

### 优先项目层级实现 & 冲突优先级解决

此规范同时适用于优化和生成。

当我们希望添加新的功能的时候，应当优先考虑在项目层实现该功能——如果其是为了服务于特定游戏场景的功能。

但是如果需要添加的功能和相当多的核心引擎功能关联，并且存在高复用可能，我们必须征求用户同意后，考虑在引擎层级上修改OpenCore来实现。

但是对于一般的游戏功能的实现，一定严禁修改OpenCore的相关代码。

#### 冲突解决

当引擎层和项目层存在为了应对同一问题的系统和结构，应当优先考虑（征求用户同意）取缔项目层的逻辑，而接入引擎层的实现。

这也是一切的前提，在生成代码之前一定要检查引擎是否已经存在了类似的逻辑。

### 可拓展性保证

对于类似于序列化/反序列化这样的功能逻辑（不仅仅局限于，只要类似这样需要长期拓展的逻辑），我们应该在生成/构造对应的结构之初就考虑到其可拓展性，方便用户进行拓展，而不应该使用临时的Magic Number or what else来糊弄

## 优化时代码规范

### 裁剪条件

优化时候应当对一些无意义的代码片段进行裁剪，裁剪的具体条件应当满足以下：

+ 确定该部分代码在当下的项目目录中未被引用
+ 该部分代码提供的功能应当是过时的，而不应该是单纯的未被使用
+ 如果该部分代码的功能仅未被使用，请确保其功能已经被其他代码代替
+ 显式标注了deprecated和todo的部分不应该被AI裁剪（交由手动裁剪）
+ 所有的裁剪应当总结后征求用户同意再裁剪
+ 多个方法提供了高度相同的功能，征求用户同意进行裁剪

对于空的代码实现，对其引用和源文件进行删除，除非用户明确标记了此处留空。

### 日志优化

日志的主体（消息部分）应该是中文，而不应该是英文。

注意，消息部分不包含LOG方法自动包含的签名和后续字符串中存在的类名和变量名。

#### 日志裁剪

对于一些明显服务于一些开发过程中的中间目标的日志，应当去除（也就是开发过程中调试用的日志，这些开发过程的目标已经完成的日志），优化到只留结果，而不留中间冗杂反复的细节日志。

#### 日志格式

其调用只需要输出消息和对应的变量状态，例如：

“加载物品失败, 物品 ID {}， 物品数量 {}”

LOG方法调用的字符串中不应该含有方法签名，因为LOG会自动加上。

### 注释优化

在进行新增注释的时候，应当保持以下习惯：

+ 不插入由大量///包裹的巨型注释块，这十分影响观感，造成源代码的割裂
+ 新增的注释应当简练和尽可能地简短，并且紧紧贴靠着其注释地代码
+ 新增的类和结构的注释应当符合Doxygen风格
+ 不在注释中加入Emoji和任何表情
+ 使用#pragma region来在一个具体的代码块内部进行不同流程的区分（要精简，不能过于详细地加入大量region）

在进行注释优化的时候，应当保持以下习惯：

+ 符合我们对“新增注释”的一切规范
+ 删除已经悬空的注释
+ 对于冗长的注释进行裁剪和优化

### 工具方法合并

对于复用性不高，而且场景单一的工具方法，直接将其在优化过程中合并进其调用位置，并使用注释或者region进行标注即可，当然，要提醒用户。


### 性能优化

注意，在此条目中提醒到的优化策略均建立在“替换可行而且无明显副作用” & “有明显必要”的前提下:

+ 使用智能指针 unique_ptr/shared_ptr/weak_ptr 来替代原本的裸指针
+ 使用 string_view 这样的现代 C++ 特性替代 const string &等等
+ 收缩int类型的尺度，如果能够在当下确定一个整数类型的尺度，那么可以收缩其尺度到我们需要的：例如如果确定这个成员不会超过255，便使用uint8替代，正负数也可以通过确定来进行收缩。
+ 紧跟上一点，如果一个成员使用整型的成本要高于float，那么便换用浮点，反之亦然。

注意，性能优化必须和用户征求同意

### 优秀功能的提升

对于那些明显适用于所有类游戏的功能，应当征求用户的同意，考虑将其提升到引擎层并取缔项目层的实现。


## 尺寸系统设计

### 绝对 or 相对 选用哪个？

我们对于UI布局中的坐标和大小，在此强烈规范，一律使用相对尺寸体系来进行设计。此举是为了适应多种不同的屏幕分辨率。


### 优化可读性

在OpenCore内部调用那些中间变量（非对外API签名），应当按照其语义给出驼峰格式的，符合美观的命名，优化时候应当考虑。

同时，可读性的优化还要向一个长逻辑中使用大括号或者#pragma region进行代码块的区分，可以加入注释。


### 公共定义提升

对于一个复用性极高的定义，例如某种样式，可以提取到一个单独的文件中。
